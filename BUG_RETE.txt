--------------------------------------------------------------------------------
1. SEGFAULT: puntatori pendenti dopo disconnessione brutale   <-- IL PIU' GRAVE
--------------------------------------------------------------------------------
File: src/Server.cpp, disconnectClient() righe 86-98

disconnectClient() fa _clients.erase(fd) ma NON toglie il client dai canali.
Il Channel continua a tenere un Client* che punta a memoria gia' liberata.

COME RIPRODURLO:
    A e B entrano in #g
    B chiude HexChat (o Ctrl-C su nc, cioe' senza mandare QUIT)
    A scrive un messaggio in #g
    -> SEGMENTATION FAULT (core dumped), server giu' per tutti

Riprodotto 2 volte su 2. Un valutatore lo trova in 30 secondi.

FIX: prima di _clients.erase(fd), scorrere tutti i canali, chiamare
     removeClient(&client), cancellare i canali rimasti vuoti e mandare agli
     altri membri il messaggio QUIT (stessa logica gia' presente in QUIT.cpp).


--------------------------------------------------------------------------------
2. CRASH GARANTITO SU Ctrl-C (core dumped)
--------------------------------------------------------------------------------
File: src/Server.cpp disconnectAll() righe 100-103, src/main.cpp riga 28

disconnectAll() itera su _clients mentre disconnectClient() fa erase sullo
stesso map -> iteratore invalidato -> fd spazzatura.

OUTPUT REALE DI VALGRIND:
    sockFd 80872704 closed.
    Warning: invalid file descriptor 80872704 in syscall close()
    terminate called after throwing an instance of 'Server::NetworkError'
      what():  Bad file descriptor
    Process terminating with default action of signal 6 (SIGABRT)

Catena: iteratore invalidato -> close() fallisce -> throw NetworkError ->
main.cpp la cattura -> richiama server.shutdown() -> rilancia dentro il catch
-> std::terminate -> SIGABRT.

Succede a OGNI Ctrl-C.

FIX: in disconnectAll() copiare prima la lista degli fd, poi chiudere;
     oppure usare l'idioma  it = _clients.begin(); while (...) { int fd =
     it->first; ++it; disconnectClient(fd); }
     In piu': disconnectClient NON deve lanciare eccezioni se close() fallisce,
     e shutdown() non va richiamato dentro il catch di main.


--------------------------------------------------------------------------------
3. 100% CPU SEMPRE (busy loop)
--------------------------------------------------------------------------------
File: src/Server.cpp riga 80 -> newClient.events = POLLIN | POLLOUT;

POLLOUT e' pronto quasi sempre (il socket ha quasi sempre spazio in scrittura),
quindi poll() ritorna subito ogni volta e non blocca mai.

MISURATO (delta di /proc/PID/stat, non media):
    0 client connessi ................... 0 % CPU
    1 client idle connesso .............. 99 % CPU
    dopo QUIT pulito .................... 100 % CPU
    dopo disconnessione brutale ......... 99 % CPU

FIX: mettere solo POLLIN di default e aggiungere POLLOUT dinamicamente
     soltanto quando il _sendBuffer di quel client non e' vuoto.


--------------------------------------------------------------------------------
4. recv() == 0 (EOF) NON GESTITO
--------------------------------------------------------------------------------
File: src/Server.cpp readBuffer() righe 24-52

readBuffer gestisce bytes < 0 e bytes > 0, ma non bytes == 0.
recv()==0 significa che il peer ha chiuso: il client va disconnesso.
Cosi' com'e', il client sparisce ma resta dentro _pfds -> POLLIN sempre attivo
-> ciclo infinito e fd mai chiuso.

MISURATO: gli fd aperti dal processo crescono soltanto, non scendono mai:
    baseline (0 client) ............. fd = 4
    1 client connesso ............... fd = 5
    dopo QUIT ....................... fd = 6
    dopo close brutale .............. fd = 7

Valgrind --track-fds conferma socket ancora aperti alla fine del processo:
    Open AF_INET socket 6: 127.0.0.1:6667 <-> 127.0.0.1:42768
       at accept (Server.cpp:75)

Test half-close (shutdown(SHUT_WR) lato client): CPU al 90% stabile.

FIX: else if (bytes == 0) { disconnectClient(fd); return 0; }


--------------------------------------------------------------------------------
5. UN ERRORE SU UN CLIENT UCCIDE TUTTI
--------------------------------------------------------------------------------
File: src/Server.cpp righe 150-164, src/main.cpp righe 22-30

Nel ciclo di run(): POLLERR -> throw NetworkError(). Stessa cosa per
recv() < 0 e per send() < 0 su un singolo fd.
main.cpp cattura l'eccezione e chiama server.shutdown() -> spegne TUTTO.

SUCCESSO DAVVERO durante i test: una batteria di test su MODE/INVITE ha
generato un POLLERR su un client e il server intero si e' spento
("server MORTO" - connessioni successive rifiutate).

FIX: un errore su un singolo fd deve disconnettere SOLO quel client e
     continuare il ciclo. Le eccezioni fatali vanno riservate agli errori
     del socket di ascolto.


--------------------------------------------------------------------------------
6. SOCKET CLIENT BLOCCANTI - viola il subject
--------------------------------------------------------------------------------
File: src/Server.cpp riga 78

    if (fcntl(_listenSock_fd, F_SETFL, O_NONBLOCK) == -1)   <-- fd SBAGLIATO
                 ^^^^^^^^^^^^^ dentro addNewClient()

Dentro addNewClient() viene rimesso O_NONBLOCK sul socket di ASCOLTO (che ce
l'ha gia' dalla riga 131) invece che su newClient.fd appena accettato.
Su Linux accept() NON eredita O_NONBLOCK: quindi TUTTI i socket dei client
sono bloccanti. Il subject richiede esplicitamente fd non bloccanti.

Conseguenza pratica: sendBuffer() fa un while che chiama send() finche' non ha
mandato tutto; su socket bloccante, con un client lento che non legge, il
server si ferma per tutti.

MISURATO: con un lettore lento e 4000 messaggi da 400 byte in coda, un nuovo
client ha impiegato 5,65 secondi a completare la registrazione.

FIX: fcntl(newClient.fd, F_SETFL, O_NONBLOCK);
     e in sendBuffer() gestire il caso n < 0 con EAGAIN/EWOULDBLOCK (uscire e
     riprovare al prossimo POLLOUT, senza considerarlo un errore).

7. CLIENT FANTASMA - std::map::operator[] crea entry
--------------------------------------------------------------------------------
File: src/Server.cpp righe 31, 42, 44, 49, 56

    _clients[fd].getRecvBuffer()      riga 31
    dispatcher.dispatch(_clients[fd]) riga 42
    _clients[fd].getQuitting()        riga 44
    _clients[fd].setRecvBuffer(...)   riga 49
    _clients[fd].getSendBuffer()      riga 56

operator[] su std::map CREA una entry vuota se la chiave non esiste.
Dopo che un client e' stato disconnesso, il ciclo di run() continua a
iterare sulla copia vfds e richiama readBuffer/sendBuffer su quell'fd,
ricreando un Client fantasma dentro _clients.

PROVA: con soltanto 2 client mai contemporanei, il bot rispondeva
    "utenti connessi al server: 4"

FIX: usare _clients.find(fd) e controllare != _clients.end() prima di usarlo.

8. BUG DEL '\r' - mangia un carattere buono
--------------------------------------------------------------------------------
File: src/Server.cpp riga 37

    if (!buffer.empty() && buffer[buffer.size() - 1] == '\r')
         ^^^^^^                ^^^^^^
        line.erase(line.size() - 1);

Controlla l'ultimo carattere di BUFFER (il resto ancora da processare) invece
che di LINE (la riga appena estratta). Quando il buffer residuo finisce per
'\r' ma la riga estratta no, taglia un carattere valido.

RIPRODOTTO SUL SERVER VIVO:
    inviato:  "PING :aaa\nPING :bbb\r"  poi  "\n"
    risposto: ":ircserv PONG ircserv :aa"    <-- manca una 'a'
              ":ircserv PONG ircserv :bbb"

Nota: e' poco visibile perche' parseMessage() in Parser.cpp ripulisce gia' da
sola \r e \n finali, quindi questa riga non serve proprio a niente ed e' solo
dannosa.

FIX: if (!line.empty() && line[line.size() - 1] == '\r')
     oppure toglierla del tutto (parseMessage la fa gia').

Sempre alla riga 37-42: mancano le graffe e l'indentazione e' fuorviante.
Solo la line.erase() e' dentro l'if, il resto (parse + dispatch) e' fuori.
Funziona ma si legge malissimo, meglio mettere le graffe.


--------------------------------------------------------------------------------
9. CONTROLLO SBAGLIATO SU signal()
--------------------------------------------------------------------------------
File: src/Server.cpp riga 118

    if (signal(SIGPIPE, SIG_IGN) != NULL)
        throw NetworkError();

signal() ritorna l'HANDLER PRECEDENTE, non un codice di errore.
Funziona solo per caso perche' SIG_DFL vale 0. Se qualcuno avesse gia'
impostato un handler per SIGPIPE, il server morirebbe all'avvio.

FIX: if (signal(SIGPIPE, SIG_IGN) == SIG_ERR)


--------------------------------------------------------------------------------
10. == INVECE DI & SUI revents
--------------------------------------------------------------------------------
File: src/Server.cpp riga 145

    if (vfds[0].revents == POLLIN)
                        ^^

revents e' una maschera di bit. Con == si perdono le connessioni quando il
kernel setta POLLIN insieme a un altro flag.

FIX: if (vfds[0].revents & POLLIN)
